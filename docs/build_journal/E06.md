# Epic E06: Compute (ECS Fargate API + Workers)

## Overview

Epic E06 implements the compute layer on top of E05's dual-VPC networking foundation.
The architecture uses ECS Fargate with a control plane (API services) and execution plane
(worker services) separated by cluster and VPC.

---

## Stories Completed

### E06-S001: Create ECS Clusters

- **Control cluster** (`infra-lab-dev-control`): On-demand Fargate only, Container Insights enabled
- **Execution cluster** (`infra-lab-dev-execution`): 1:3 Fargate/Spot ratio for cost optimization
- Both clusters have ECS Exec logging to CloudWatch

---

### E06-S002: Task Execution and Task Roles (Least Privilege)

- **Task Execution Role**: pulls images, writes logs, reads secrets from Secrets Manager
- **API Task Role**: SQS publish + S3 read/write (scoped to `infra-lab-dev-*` resources)
- **Worker Task Role**: SQS consume + S3 read/write (scoped to `infra-lab-dev-*` resources)

---

### E06-S003: API Service (ALB + Target Groups + Health Checks)

- ALB with TLS 1.3 (`ELBSecurityPolicy-TLS13-1-2-2021-06`)
- HTTP to HTTPS redirect
- Blue + Green target groups with `/health` check (200 OK, 30s interval)
- Test listener on port 8443 for blue/green pre-production validation
- `drop_invalid_header_fields = true` (CKV_AWS_131)

---

### E06-S004: Blue/Green Deployment (CodeDeploy)

- CodeDeploy ECS application with canary 10% / 5 minute strategy
- Auto-rollback on deployment failure
- Test traffic route for validation before promotion
- CodeDeploy IAM role with `AWSCodeDeployRoleForECS` managed policy

---

### E06-S005: Worker Services (Tiered)

| Tier | CPU | Memory | Desired | Use Case |
| --- | --- | --- | --- | --- |
| nano | 256 | 512 MiB | 1 | Notifications, webhooks |
| medium | 1024 | 2048 MiB | 1 | Data transforms, reports |
| xlarge | 4096 | 8192 MiB | 0 | ML inference, batch (scale-from-zero) |

All workers run on the execution cluster (FARGATE_SPOT preferred).

## Modules Created

### `infra/modules/ecs_cluster`

- Configurable capacity provider strategy (FARGATE + FARGATE_SPOT)
- CloudWatch Container Insights
- ECS Exec logging with optional KMS encryption
- Outputs: cluster_id, cluster_arn, cluster_name, exec_log_group_name

### `infra/modules/ecs_service`

- Fargate task definition with configurable CPU/memory
- Service with deployment circuit breaker
- Optional ALB integration (target group ARN)
- Blue/Green or rolling deployment controller
- CloudWatch log group with optional KMS encryption
- Outputs: service_id, service_name, task_definition_arn, log_group_name

## Architecture Decisions

1. **Dual cluster model**: Control plane workloads get on-demand Fargate (reliability).
   Execution plane workers get Spot (cost savings, fault-tolerant).

1. **Scale-from-zero**: XLarge workers start at desired_count=0 and scale up
   via autoscaling when queue depth increases.

1. **Blue/Green over rolling**: API service uses CodeDeploy with canary deployment
   for safer production releases and instant rollback capability.

1. **Least-privilege IAM**: Each service tier gets its own task role scoped to
   only the AWS actions it needs (SQS, S3).
